# Задание 4. Продажа ОСАГО

Схема: `InsureTech_C4_container-diagram_osago.drawio` (рядом png-экспорт).
Это диаграмма из задания 3 плюс `osago-aggregator`, его хранилище, новые связи
и обозначения паттернов отказоустойчивости.

## Что требуется от решения

- 2,5 тысячи пользователей одновременно заполняют заявку.
- Заявка уходит во все страховые (сейчас пять, скоро десять), у каждой два
  REST-эндпоинта: создать заявку, получить предложение.
- Предложение каждой страховой показывается сразу, как только пришло.
- Ждём решение не дольше 60 секунд.
- Подход из задания 3 сохраняем: обмен между сервисами идёт событиями.

Оценка нагрузки на исходящие вызовы: 2 500 заявок × 10 страховых = 25 000
внешних заявок в пике, и по каждой опрос статуса раз в 5 секунд до ответа. Это
до 5 000 исходящих запросов в секунду при худшем сценарии, по 500 на каждую
страховую. Отсюда и решения ниже.

## osago-aggregator

**Хранилище: нужно.** Заявка живёт до 60 секунд, но экземпляров сервиса
несколько, и кто-то должен помнить, в какие страховые заявка уже ушла, какой у
неё внешний идентификатор, кто ответил, когда следующий опрос и когда дедлайн.
Держать это в памяти пода нельзя: под перезапустится или HPA его уберёт, и
заявка потеряется. Хранилище это своя схема в PostgreSQL, таблица маленькая,
строки удаляются через час. Redis с TTL тоже подошёл бы, но PostgreSQL уже
есть, а `SELECT ... FOR UPDATE SKIP LOCKED` даёт простое разделение работы между
подами без отдельного координатора.

**API для core-app:**

- Вход: события `osago.applications` в Kafka (ключ `applicationId`). Публикует
  их `core-app` через тот же outbox, что и оформленные страховки.
- Выход: события `osago.offers`, по одному на ответ каждой страховой, включая
  отказ и таймаут, чтобы `core-app` знал, что ждать больше нечего. Таблица
  состояния заявок здесь же служит outbox: строка помечается опубликованной
  только после подтверждения от Kafka, неопубликованное досылает фоновый цикл.
  Отдельный Debezium ради одной таблицы не нужен, at-least-once обеспечивается
  этим циклом, дубли `core-app` отсекает по паре заявка плюс страховая.
- REST `GET /applications/{id}` для чтения текущего состояния и уже полученных
  предложений. Нужен, когда веб-клиент переподключился и часть событий уже
  ушла.

Со стороны `core-app` агрегатору ничего, кроме топиков, не нужно: обратной
связи по REST нет, результат он узнаёт из `osago.offers`.

## Интеграция core-app и osago-aggregator

Kafka, как в задании 3. Синхронный REST здесь не подходит: `core-app` не должен
держать соединение 60 секунд и не должен падать, если агрегатор недоступен.
Заявка сохраняется в `core-db`, событие уходит через outbox, дальше
`osago-aggregator` работает сам.

## API веб-приложения и интеграция с core-app

- Создание заявки остаётся REST: `POST /osago/applications`, ответ `202` с
  идентификатором заявки.
- Предложения веб получает через Server-Sent Events:
  `GET /osago/applications/{id}/offers/stream`. Это новая стрелка на схеме.

Почему SSE, а не WebSocket или polling. Поток здесь односторонний, от сервера к
клиенту, WebSocket с его двунаправленным каналом и отдельным протоколом
избыточен. SSE живёт поверх обычного HTTP, браузер сам переподключается и
присылает `Last-Event-ID`, по которому `core-app` дошлёт пропущенное. Polling
раз в секунду от 2,5 тысяч пользователей это лишние 2,5 тысячи RPS и задержка
показа до секунды.

Что придётся настроить на пути SSE, иначе поток не дойдёт: на ingress-nginx для
этого location выключить буферизацию ответа (`proxy_buffering off`) и поднять
`proxy-read-timeout` до 90 с, у ALB idle timeout тоже 90 с. Таймаут больше
дедлайна заявки на 30 с специально: последнее событие приходит на 60-й секунде,
и соединение не должно рваться ровно в этот момент.

Что видел клиент, хранится: `core-app` записывает каждое полученное
предложение в `core-db` рядом с заявкой на ОСАГО, а при оформлении фиксирует
выбранное. Это ответ на проблему "нечем разбирать спорные случаи" из третьего
задания, короткий срок жизни строк в `osago-aggregator-db` и суточное хранение
в топике на это не влияют.

## Несколько экземпляров сервисов

От этого зависит и решение, и его детали.

- **core-app.** SSE-соединение живёт на одном поде, а событие из Kafka в
  обычной consumer group получит один произвольный под. Поэтому каждый экземпляр
  `core-app` читает `osago.offers` в своей consumer group (broadcast) и отдаёт
  клиенту только события заявок, чьи SSE-соединения держит сам. Издержки
  понятные: каждый под читает весь топик, а при масштабировании 2..10 подов
  группы плодятся, их offsets чистятся по `offsets.retention.minutes`. Топик
  короткий, хранение сутки, это терпимо. Если трафик вырастет, следующий шаг
  это Redis pub/sub, он уже есть в инфраструктуре как кеш, но пока это лишний
  путь данных ради того же результата.
- **osago-aggregator.** Заявку из Kafka получает один под, он создаёт заявки в
  страховых и записывает строки в БД. Опрос делает любой свободный под: берёт
  строки с истёкшим временем опроса через `SKIP LOCKED`, спрашивает страховую,
  обновляет строку. Повтор создания заявки после падения пода безопасен, если
  API страховой принимает ключ идемпотентности (наш `applicationId`). Это
  допущение, его надо подтвердить по каждому партнёру при подключении; там, где
  ключа нет, повтор создания не делаем, а сначала спрашиваем статус.
- **Порядок событий.** Ключ партиционирования это `applicationId`, события
  одной заявки идут по порядку.

## Паттерны отказоустойчивости

Обозначения из библиотеки курса, на схеме иконки стоят у соответствующих
стрелок.

| Где | Паттерн | Зачем |
|---|---|---|
| osago-aggregator → страховые | Timeout 5 с на вызов, 60 с на заявку целиком | Медленная страховая не задерживает остальных, по дедлайну отдаём "нет ответа" |
| osago-aggregator → страховые | Retry до 3 раз с экспоненциальным backoff | Только для создания заявки (идемпотентно) и опроса, сетевые ошибки и 5xx |
| osago-aggregator → страховые | Circuit Breaker на каждую страховую | Упавший партнёр отключается на минуту, заявки не ждут его таймаутов |
| osago-aggregator → страховые | Rate Limiter на каждую страховую | Соблюдаем лимиты партнёров, 500 RPS на одного в пике это уже повод. Если лимит партнёра ниже расчётной нагрузки, интервал опроса растёт адаптивно, а заявки, не успевшие к дедлайну, получают событие "нет ответа"; доля таких заявок это метрика для разговора с партнёром о лимите |
| Веб → core-app (ingress) | Rate Limiter на пользователя и IP, Timeout SSE 90 с | Защита от накрутки заявок и висящих соединений |
| Партнёры → core-app (api-gateway из задания 1) | Rate Limiter 20 RPS на партнёра | Проблема из постановки задачи. На C4-схеме шлюз не показан как контейнер, это инфраструктурный слой, иконка стоит на стрелке |
| core-app → client-info | Timeout, Retry, Circuit Breaker | Синхронный REST на пути оформления |
| core-app → osago-aggregator (REST) | Timeout | Чтение состояния при переподключении, не должно висеть |
| ins-product-aggregator → страховые | Timeout, Retry, Circuit Breaker | Те же внешние API, те же проблемы |
| ins-comp-settlement → страховые | Timeout, Retry | Ночная передача реестра, ошибку проще повторить утром, чем размыкать цепь |

Для обмена через Kafka отдельные значки не рисую: таймауты и повторы у
продюсера и консьюмера встроены в клиент, а сообщения, которые не удалось
обработать после повторов, уходят в DLQ, как описано в третьем задании.
