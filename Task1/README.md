# Задание 1. Технологическая архитектура to-be

Схема: `InsureTech_технологическая архитектура_to-be.drawio` (рядом png-экспорт).
Нотация та же, что в схеме as-is: объекты из библиотек Yandex Cloud, зона
доступности, кластер, VM, сервис внутри.

Ниже коротко то, что на схеме вынесено в комментарии, плюс расчёты, которым на
схеме места нет.

## Исходные требования

| Требование | Значение | Как закрываю |
|---|---|---|
| Доступность | 99,9 % (8,7 ч простоя в год) | Две зоны доступности active-active, автоматический failover БД |
| RTO | 45 мин | Отказ узла или зоны: минуты, автоматически. Полное восстановление из бэкапа: до 35 мин |
| RPO | 15 мин | Синхронная реплика (RPO 0 при отказе узла), WAL в Object Storage раз в минуту, RPO при потере кластера не больше лага реплики плюс минута |
| Одинаковое время загрузки по регионам | Не зависит от географии | CDN для статики, единый адрес входа, все вычисления в одном регионе |
| Объём данных | 50 ГБ | Один инстанс PostgreSQL с запасом, без шардирования |

## Масштабирование

Приложение масштабирую горизонтально. Все четыре сервиса stateless, они уже в
Kubernetes, поэтому HPA по CPU и памяти плюс cluster autoscaler на node group
закрывают и рекламную кампанию, и рост регионов. Вертикальное масштабирование
подов даёт только больший под, но не убирает единую точку отказа и упирается в
размер узла.

Базу масштабирую вертикально: 50 ГБ и 10 RPS оформления это нагрузка, которую
один инстанс PostgreSQL держит с большим запасом. Чтение каталога уходит на
синхронную реплику и в Redis, запись остаётся на primary.

Зоны: две полноценные (приложение и БД) и третья только под кворум Patroni/etcd
и асинхронную реплику. Одна зона не даёт 99,9 %: инциденты и плановые работы
уровня зоны случаются в облаках чаще, чем один раз на 8,7 ч в год, и бюджет
простоя уходит на них целиком. Три полных копии приложения избыточны по
стоимости при текущей нагрузке.

## Kubernetes: независимые кластеры в каждой зоне

Выбрал два зональных кластера вместо одного растянутого регионального.

За: домен отказа совпадает с зоной, ошибка control plane или неудачное
обновление K8s не затрагивает вторую зону; обновления и раскатки идут по
кластерам поочерёдно под живым трафиком; нет межзонного трафика между подами.

Цена: два целевых кластера в CI/CD. Решается одним набором манифестов и ArgoCD,
который применяет их в оба кластера, плюс алерт на дрейф конфигурации.

Растянутый кластер отверг: при потере зоны с частью control plane деградирует
весь кластер, а единственный плюс это один kubectl.

## Балансировка и health check

1. Cloud DNS отдаёт один публичный адрес Application Load Balancer, TTL 60 с.
   Балансировщик региональный, за одним адресом стоят обе зоны.
2. ALB (L7) держит две backend-группы, по одной на зону, вес 50/50. Health
   check `GET /healthz` на ingress каждой зоны раз в 2 с, три неудачи подряд
   выводят зону из ротации, то есть через 6 с после отказа.
3. Внутри кластера ingress-nginx балансирует на поды по readiness probe,
   liveness перезапускает зависшие поды.
4. Партнёрский API заходит через тот же ALB на api-gateway с лимитом на
   партнёра (20 RPS по договору). Проблема одного партнёра на 250 RPS
   закрывается здесь, а не ресурсами приложения.
5. БД: внутренний Network Load Balancer с двумя целевыми группами. `db-rw`
   проверяет Patroni REST API `:8008/primary` (200 только на лидере), `db-ro`
   проверяет `:8008/sync` (200 только на синхронной реплике). Асинхронную
   реплику в зоне D в пул чтения не пускаю: она отстаёт и с неё снимаются
   бэкапы. Приложение подключается к двум постоянным адресам и не знает, кто
   сейчас primary.
6. Мониторинг собирает метрики и логи из обоих кластеров и с VM БД, делает
   внешнюю проверку `/health` с трёх точек раз в 30 с и алертит в Telegram и
   по телефону. Это ответ на "узнали о падении от пользователей".
7. Исходящие вызовы в страховые компании идут через NAT Gateway с фиксированным
   адресом, который партнёры вносят в свои белые списки. Таймауты и повторы на
   этих вызовах разобраны в заданиях 3 и 4.

## Failover

Active-active по зонам на уровне клиента: один домен, обе зоны обслуживают
запросы одновременно, сессии в JWT, состояние только в БД и Redis, поэтому любой
запрос может уйти в любую зону.

- Отказ зоны с приложением: ALB убирает её backend-группу по health check за
  6 с. При 50 RPS это до 300 запросов, попавших в мёртвую зону, ретрай на
  стороне веб-приложения скрывает их от пользователя, партнёрам по API
  прилетает 502 и повтор на их стороне.
- Отказ primary БД: Patroni за 30 до 60 с продвигает sync standby, NLB
  переключает `db-rw` по health check, приложение переподключается по тому же
  адресу. Запись недоступна примерно минуту, чтение продолжается с реплики.
- Отказ зоны B, где стоит sync standby: primary жив, Patroni в режиме
  `synchronous_mode: on` без `strict` переводит запись в асинхронный режим и
  назначает синхронной репликой ноду в зоне D. Запись не останавливается, окно
  с RPO больше нуля длится до переназначения, и это осознанный выбор:
  доступность записи здесь важнее строгого RPO 0, потому что RPO 15 мин всё
  равно покрыт архивом WAL.
- Потеря всего кластера БД: VM поднимаются из Terraform-описания, Patroni
  собирает кластер из бэкапа в Object Storage.

Всё это внутри RTO 45 мин, а синхронная реплика даёт RPO 0 при отказе одного
узла.

## Конфигурация базы данных

Patroni-кластер из трёх нод PostgreSQL 16 на VM: primary в зоне A, sync standby
в зоне B, async standby в зоне D. DCS это etcd по одной ноде на каждой VM,
кворум 2 из 3 переживает потерю любой зоны.

Резервное копирование: WAL-G с асинхронной реплики в зоне D, чтобы не грузить
primary. Для этого на всех нодах `archive_mode = always`, а на primary
`archive_timeout = 60`, чтобы сегмент WAL закрывался не реже раза в минуту даже
при слабой записи. Базовый бэкап раз в сутки в 03:00, хранение 30 дней.

Расчёт под требования:

- RPO при потере всего кластера равен лагу асинхронной реплики плюс минута на
  архивирование. В норме лаг секунды, алерт стоит на лаг больше 5 мин, так что
  худший случай остаётся внутри требуемых 15 мин.
- RTO при полном восстановлении: 50 ГБ из Object Storage на VM в том же регионе
  разворачиваются за 15 до 25 мин, VM и Patroni поднимаются из Terraform за
  5 до 10 мин параллельно, ещё 5 мин на переключение приложения. Итого до 35
  мин против 45. Восстановление проверяется ежемесячно на отдельной VM, иначе
  цифры остаются на бумаге.

Слоты логической репликации (их будет использовать Debezium из задания 3)
объявлены в Patroni как `permanent_slots`, иначе после failover коннектор
потеряет позицию.

## Шардирование

Не применяю. 50 ГБ и профиль нагрузки не требуют его даже после кампании,
а шардирование добавит межшардовые запросы, сложность миграций и второй уровень
failover. Возвращаться к вопросу имеет смысл при росте к 1 ТБ или к тысячам RPS
записи, и тогда первым кандидатом будет разнос схем сервисов по отдельным
кластерам БД, а не шардирование одной схемы.

## Одинаковое время загрузки по регионам

Все зоны доступности находятся в одном регионе, поэтому динамическая часть
ответа для пользователя из Калининграда и из Хабаровска идёт по одному пути и
отличается только сетевой задержкой до региона. Её убираю там, где она заметна:
статика веб-приложения (JS, CSS, картинки) раздаётся через CDN с точек
присутствия по стране, ответы API маленькие. Разворачивать второй регион с
репликацией данных при 50 ГБ и текущем RPS не оправдано, это решение на
следующий этап роста.
