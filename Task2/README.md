# Задание 2. Динамическое масштабирование контейнеров

## Файлы

| Файл | Что это |
|---|---|
| `deployment.yaml` | Deployment тестового приложения, 1 реплика, лимит памяти 30Mi |
| `service.yaml` | Service типа NodePort, доступ через `minikube service scaletestapp --url` |
| `hpa.yaml` | HorizontalPodAutoscaler по утилизации памяти 80 %, от 1 до 10 реплик |
| `locustfile.py` | Сценарий нагрузки из задания |
| `demo.sh` | Прогон от начала до конца: кластер, манифесты, нагрузка, логи |
| `logs/` | Логи прогона: HPA и поды до, во время и после нагрузки |
| `screenshots/` | Дашборд Kubernetes во время прогона |

## Как воспроизвести

```bash
pip install locust
./demo.sh                      # USERS=400 SPAWN=40 DURATION=4m по умолчанию
minikube dashboard             # отдельно, для скриншотов
```

На Apple Silicon образ из ghcr.io не подходит, там только amd64. Собирается из исходников курса
прямо в кластер: `minikube image build -t ghcr.io/yandex-practicum/scaletestapp:latest .`

Скрипт поднимает Minikube, включает metrics-server, применяет три манифеста,
ждёт первые метрики, запускает `kubectl get hpa -w` и `kubectl get pods -w` в
фон, прогоняет locust без веб-интерфейса и складывает всё в `logs/`.

## На что обратить внимание в манифестах

**Requests и limits.** HPA считает утилизацию памяти как отношение фактического
потребления к `requests`, а не к `limits`. Лимит 30Mi задан условием, request
10Mi подобран так, чтобы простой приложения (небольшой бинарник на Go в образе
scratch) сидел ниже целевых 80 % от request, а под нагрузкой потребление
уходило за порог 8Mi и HPA добавлял реплики. Если поставить request равным
лимиту, целевые 24Mi приложение под такой нагрузкой не наберёт и
масштабирование не сработает вовсе. Фактические цифры простоя и пика видны в
`logs/01_before.log` и `logs/04_top_every_15s.log`.

**Поведение HPA.** Вверх без окна стабилизации и с удвоением раз в 15 с, чтобы
пик не успел уронить поды по OOM. Вниз с окном 60 с и по две реплики за 30 с:
дефолтные 5 минут для демонстрации слишком долго, а для продакшена такое окно
я бы вернул к 300 с, чтобы не дёргать реплики на каждом провале трафика.

**Пробы.** Readiness на `/metrics`, чтобы под попадал в Service только когда
HTTP-сервер поднялся. Это важно именно при масштабировании: новые реплики
появляются под нагрузкой, и трафик на неготовый под даёт ошибки.

## Результат прогона

Прогон 16.09, 1000 пользователей locust, 4 минуты. В простое под держал 4 до 7Mi
(40 до 70 % от request 10Mi). Через минуту после старта нагрузки утилизация
подскочила до 291 %, и HPA пошёл вверх: 1 → 2 → 4 → 5 → 7 → 9 реплик за
три с половиной минуты, дальше нагрузка кончилась. Хронология в
`logs/02_hpa_watch.log`, появление подов в `logs/03_pods_watch.log`, память
каждого пода раз в 15 с в `logs/04_top_every_15s.log`, события HPA с временем
каждого шага в `logs/06_after_load.log`.

Что заметил по ходу:

- Вниз реплики не ушли. Через 12 минут после нагрузки HPA всё ещё показывает
  80 % и 9 реплик (`logs/07_after_cooldown.log`). Go после пика не отдаёт
  память системе, working set остаётся высоким, а HPA по памяти видит именно
  его. Это известное свойство масштабирования по памяти: вверх оно реагирует
  хорошо, вниз почти никак. Для боевых сервисов метрику памяти стоит сочетать с
  CPU или с числом запросов, иначе после каждого пика будем платить за лишние
  поды до ручного вмешательства.
- 6 % запросов locust оборвались (`logs/05_locust.log`). Причина видна в
  `logs/07_after_cooldown.log`: у двух первых подов RESTARTS 2 и 1, на пике,
  пока HPA ещё не добавил реплики, они упёрлись в лимит 30Mi и были убиты по
  OOM. Это в точности проблема из условия задания, и HPA её снял: как только
  подов стало больше, перезапуски прекратились, остальные реплики прожили
  нагрузку без единого рестарта.
- Первый замер простоя на 36-й секунде жизни пода показал 2Mi, и request 6Mi
  по нему оказался занижен: после первой сборки мусора под сел на 6Mi и HPA
  раскрутил реплики без всякой нагрузки. Request 10Mi выбран уже по замеру
  установившегося простоя.

Скриншоты дашборда во время нагрузки лежат в `screenshots/`.
