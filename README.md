# InsureTech: highload и realtime

Проектная работа 8 спринта курса "Архитектор программного обеспечения".
Кейс InsureTech: агрегатор страховых продуктов, который упёрся в собственную
архитектуру перед рекламной кампанией.

| Задание | Что сделано | Где |
|---|---|---|
| 1. Технологическая архитектура | Две зоны доступности, независимые кластеры, ALB с health check, Patroni-кластер PostgreSQL, бэкапы в Object Storage, решение по шардированию | [Task1](Task1) |
| 2. Динамическое масштабирование | Deployment, Service, HPA по памяти, прогон под нагрузкой locust, логи и скриншоты | [Task2](Task2) |
| 3. Event-Driven архитектура | Список проблем и рисков, обновлённая диаграмма контейнеров с Kafka и Transactional Outbox | [Task3](Task3) |
| 4. Продажа ОСАГО | osago-aggregator, SSE для веба, события для сервисов, паттерны отказоустойчивости на схеме | [Task4](Task4) |
| 5. GraphQL API | Схема client-info, покрывающая REST-контракт, примеры запросов | [Task5](Task5) |
| 6 | В задании нет шестого пункта, директория оставлена по требованию к структуре репозитория | [Task6](Task6) |

Схемы сделаны в draw.io, рядом с каждым `.drawio` лежит png-экспорт, чтобы
смотреть без редактора. В Task1 использована нотация Yandex Cloud, как в схеме
as-is, в Task3 и Task4 нотация C4 из исходной диаграммы контейнеров.

Сквозная логика по заданиям: проблемы из постановки (медленные страницы,
партнёр на 250 RPS, падения, о которых узнают от пользователей) закрываются в
первом задании на уровне инфраструктуры, а третье и четвёртое убирают
синхронные зависимости от внешних систем, из-за которых приложение и было
"узким горлышком".
