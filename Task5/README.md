# Задание 5. GraphQL API для client-info

Схема лежит в [client-info.graphql](client-info.graphql).

## Что было в REST

Три ресурса, все только на чтение:

| Ресурс | Что возвращает |
|---|---|
| `GET /clients/{id}` | `Client`: id, name, age |
| `GET /clients/{id}/documents` | список `Document`: id, type, number, issueDate, expiryDate |
| `GET /clients/{id}/relatives` | список `Relative`: id, relationType, name, age |

Сценарий "оформить страховку" сейчас это три HTTP-вызова подряд, а с ростом
карточки до 500 атрибутов ресурсов станет десятки. Либо потребитель делает
много запросов, либо получает один огромный объект.

## Как сделал в GraphQL

- Три типа один в один с REST: `Client`, `Document`, `Relative`. Поля назвал
  так же, чтобы миграция потребителей была механической.
- `documents` и `relatives` стали полями `Client`, а не отдельными ресурсами.
  Потребитель перечисляет только то, что ему нужно, сервис отдаёт ровно это.
- Запросы: `client(id)` покрывает все три REST-операции, `clients(ids)` даёт
  забрать пачку клиентов одним вызовом, `clientDocuments` и `clientRelatives`
  оставил как прямые аналоги старых ресурсов на время миграции потребителей,
  после неё их можно убрать, вложенные поля делают то же самое.
- `type` документа и `relationType` перевёл из строки в enum: в контракте
  список значений не задан, и каждый потребитель держал свой. Список в схеме
  надо сверить с командой client-info, я взял очевидный.
- Даты выдачи и окончания документа сделал скаляром `Date` вместо строки,
  `activeOnly` у документов отсекает просроченные по `expiryDate`.

## Примеры запросов

Веб-приложение показывает шапку личного кабинета, ему нужны только имя и
паспорт:

```graphql
query Header($id: ID!) {
  client(id: $id) {
    name
    documents(type: PASSPORT, activeOnly: true) {
      number
    }
  }
}
```

core-app оформляет страховку жизни и хочет всё сразу, одним вызовом вместо трёх:

```graphql
query ForPolicy($id: ID!) {
  client(id: $id) {
    id
    name
    age
    documents { type number issueDate expiryDate }
    relatives { relationType name age }
  }
}
```

ins-comp-settlement строит реестр по списку клиентов:

```graphql
query Registry($ids: [ID!]!) {
  clients(ids: $ids) {
    id
    name
  }
}
```

## Что это даёт client-info

Число вызовов на сценарий падает до одного, объём ответа определяет потребитель,
а не сервис. При этом появляются свои обязанности: резолверы вложенных полей
нужно собирать батчами (DataLoader), иначе `clients(ids)` с вложенными
документами превратится в N+1 запросов к БД; на глубину и стоимость запроса
нужен лимит, чтобы один потребитель не собрал всю карточку целиком через
вложенность.
